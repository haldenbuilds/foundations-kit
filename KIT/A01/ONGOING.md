# Continuing work

## Resume from files

On every later session read `SCALE-PLAN.md`, `DECISIONS.md`, and the newest `NUMBERS.md` rows in the owner's folder. Then read the saved brief, source inventory, parked-work register, task board, risk register, and `SESSION.md` where needed. Confirm the last completed step and next act. Do not reconstruct facts from chat memory. If records are missing, say which, ask the owner to restore them, and draft a recovery note. If sources conflict, stop the affected recommendation and log the conflict.

One current plan lives in `SCALE-PLAN.md`. Save its prior version before an approved update. Observations and decisions are append-only; correct with a new dated row linked to the old one. An interrupted write is a draft, not the current plan: recover the last complete version, compare, and obtain the required permission before replacing it. Each saved version names its sources, decisions, and next review.

## Weekly review and rolling plan

The owner starts this loop by saying `Weekly review` and bringing current records. This package schedules no background jobs and promises no automatic contact.

1. Re-read actuals and source dates. Add the new weekly numbers once. Keep forecasts, actuals, and owner thresholds separate. Missing or stale evidence stays UNKNOWN; ask for the smallest missing record.
2. Compare each task's done-check with its evidence. Record complete, running, blocked, or stopped with a reason. A failed check is not complete.
3. Re-run the capacity, cash, and buyer-path diagnostic in `AGENT-INSTRUCTIONS.md`. Name the next constraint, which can be the same as last week or UNKNOWN. Preserve a running test until its evidence condition is met; an immediate cash or delivery stop is recorded explicitly rather than silently switching tests.
4. Save the old plan, keep unfinished justified tasks, retire completed tasks, and add the next week so the current horizon covers four weeks. Keep one current move. A move changes only from new evidence and the owner's adoption of the revised plan. Log why.
5. Write the next act, owner, review date, and blockers in `SESSION.md`. Show the owner what changed and the evidence used. If you have the Foundations Kit, use P06 for the cadence, P12 for actual money and pipeline readings, P02 for targets, and C08 for the handoff. Otherwise the files above carry the same information.

## Decision helper

On `Help me decide`, write the decision, evidence, constraints, options including doing nothing, and the cost and reversibility of each. Recommend one option with its reason, uncertainty, and an observable check. Convert it into ordered tasks with owners, inputs, done-checks, and dates the owner accepts. The owner's decision, exact subject version, words, actor, time, and review trigger go to `DECISIONS.md`; recommendations never masquerade as decisions.

If you have the Foundations Kit, open P04 and write the tasks to the owner's P04 board, and open P05 and write the decision, risks, triggers, and mitigations to the owner's P05 register. Cross-link the C07 decision ID, with no competing decision history. Confirm the owner's real board and register locations first. Otherwise use `TASKS.md` and `RISKS.md` in the owner folder. A task row has ID, next action, priority, dependency, owner, due date, done-check, state, and decision ID. A risk row has ID, type, statement, owner, trigger, mitigation, state, and decision ID. Reading a kit template alone is not a board update. If writing is unavailable, give the owner those exact rows and leave persistence unconfirmed until saved.

## Task breakdown

On `Break this down`, name the result and source decision. Split it into the smallest actions a named person can perform, in dependency order. Each action has an input, owner, output, done-check, and stop condition. Flag tasks needing a missing input or an external approval. Do not add a tool purchase or live action under a writing task. Put the rows in the same board as the decision helper. Start only ready work inside the current authority.

## Maintenance and help

On `Show parked work`, read the durable PARK rows in `SCOPE.md`, including source, reason, owner, dependencies, and wake condition. The owner decides whether to reactivate them. Recheck thresholds and measurement periods when the business or recording method changes. Recheck the package after an approved file change. On `Help: [question]`, answer from the shipped guides with a filename and section. If unsupported, say UNKNOWN-IN-GUIDES and name the missing owner decision or qualified advisor question. Continued planning support lasts as long as the owner retains and updates these files.
